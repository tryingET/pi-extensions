## 1. Background and problem statement

### 1.1 Why this RFC exists now

Three independent threads converged on 2026-08-24:

1. **Upstream shipped what we asked for.** We filed earendil-works/pi#8175 ("Expose
   compaction failures to extension handlers", local tracker:
   `softwareco/infra/issue-tracker/pi-mono-upstream/compaction-failure-extension-events.md`).
   Upstream triage automation auto-closed it `NOT_PLANNED` within ~1 minute with the
   `untriaged` label (same flow as #6000). Despite that closure, **0.84.3 shipped the
   feature** as the `session_compact_failed` extension event. The issue did not fail
   because of our code or a rejected design — it failed an automation gate and won on
   merit anyway.
2. **The runtime moved.** Installed pi is now 0.84.3. All surfaces described here are
   live in `/home/tryinget/.npm-global/lib/node_modules/@earendil-works/pi-coding-agent`.
   Our extensions were built against 0.84.0/0.84.1-era contracts.
3. **We have a standing observability blind spot.** pi-telemetry attributes ~1,400 of
   ~1,800 compactions over a 30-day window as "stalled" via an unresolved-begins
   heuristic, because failure error text was unreachable by construction before this
   event existed.

### 1.3 Verified upstream contract (from installed 0.84.3 types)

`dist/core/extensions/types.d.ts` (installed 0.84.3):

```ts
/** Fired after context compaction fails or is aborted */
export interface SessionCompactFailedEvent {
    type: "session_compact_failed";
    /** What triggered the compaction: manual /compact, the context threshold, or context overflow recovery */
    reason: "manual" | "threshold" | "overflow";
    /** Error text when compaction failed for a non-abort reason. */
    errorMessage?: string;
    /** True when compaction was cancelled or aborted. */
    aborted: boolean;
    /** True when the aborted turn would have been retried after this compaction (overflow recovery) */
    willRetry: boolean;
    /** True when the failing compaction content came from a session_before_compact handler. */
    fromExtension: boolean;
}
```

Handler registration: `pi.on("session_compact_failed", handler)` where handler is
`ExtensionHandler<SessionCompactFailedEvent>` (no result type — observers only).

### 1.4 Operational note: restart Pi sessions after `pi update` (added 2026-08-24, post-ADR)

The 0.84.3 update itself surfaced a transient failure mode while being applied:
long-running Pi processes that survived the on-disk update later failed their first
`openai-completions` API call with `The requested module './simple-options.js' does
not provide an export named 'clampThinkingBudgetToAnswerRoom'`. Verified cause
(`contrib/pi-mono` `v0.84.2..v0.84.3`): both the export and its named import were added
together in pi-ai 0.84.3, but a process started under 0.84.2 still held the old
`simple-options.js` in its ESM cache; Node then lazily loaded the new
`openai-completions.js` from disk against the cached old exporter. The on-disk tree
was never inconsistent and no code change is required — the remediation is
procedural: **restart Pi sessions after `pi update`** (observed healing after
restart). The same mixed-module race, not the update payload, terminated the final
turn of the authoring session.

## 4. Proposed changes

Ranked by value/risk ratio. Items P0–P2 are in-scope for this RFC; P3 is follow-up.

**Execution authority:** before implementation, author the P0/P1 work packages as AK
tasks scoped to their owning packages (`ak task` from the monorepo root; repo identity
is the monorepo root, not package folders). This RFC is the design input; AK tasks are
the execution authority per lane policy.

### P0-A — pi-telemetry: adopt `session_compact_failed` (primary)

Replace the unresolved-begins heuristic's blind spot with causal data.

**Correlation keying (new design — none exists today):**
- `collector.ts` currently appends events keyed only by `sessionId`. Introduce a
  synthesized correlation key: a composite of `(sessionId, compactionSeq)` where
  `compactionSeq` is a per-session monotonic counter assigned when a
  `compaction_begin` record is written, and stamped onto every subsequent
  compaction-family record (`compaction`, `compaction_failed`, `stalled_unknown`)
  in that session until the next begin.
- **Seq lifetime across session replacement (decision):** the counter is scoped to
  the active collector session context and resets whenever pi replaces the session
  file (resume-with-new-file, fork, `new`). Uniqueness is preserved by the composite
  key, never by seq alone. Cross-session dashboards MUST group by `sessionId`
  before aggregating by seq; no cross-session counter is attempted. This keeps the
  design correct regardless of whether a given resume reuses or recreates the
  session file.
- Terminal-state machine (exhaustive):

| From \ Event | `session_compact` | `session_compact_failed` | neither at window close |
|---|---|---|---|
| begin | resolved-success | resolved-failure (+cause) | stalled-unknown |
| begin → failed → retry → success | resolved-success-after-retry (canonical record; the failed record remains as history with `retried: true` backfilled on success) | — | — |
| orphan failed (no prior begin; e.g. compaction started before extension load) | — | resolved-failure, flagged `orphan: true` | — |

- Canonicality rule: each `(sessionId, compactionSeq)` pair resolves to exactly
  **one** terminal
  outcome; intermediate failures stay as history records and never count toward
  failure totals on their own.
- Classification rule (decision): `aborted && willRetry === true` records are tagged
  `recoverable` and reported as a **separate recoverable class**, excluded from
  hard-failure/SLO counts. Aborts with `willRetry === false` count as failures with
  null cause.
- `errorMessage` may be undefined on aborts; store nulls explicitly, never fabricate.
- `fromExtension: true` failures are tagged separately: they implicate a
  `session_before_compact` handler (potentially ours) rather than the provider.

**Data-semantics migration (telemetry consumers):**
- Introduce a telemetry record schema-version field (none exists today;
  `collector.ts` records carry no version marker) and set it on first
  `compaction_failed` emission. Pre-existing records are treated as version 0 by
  consumers.
- Historical "stalled" attributions are **never rewritten**: the old heuristic's
  outputs remain valid for pre-upgrade windows; the causal classes start at the
  schema-version boundary. Dashboards partition on schema version, not timestamps.
- Expected effect going forward: stalled-unknown shrinks to genuinely lost events
  only (host crash between begin and terminal event).

Acceptance:
- Unit tests covering every row of the transition table above, including orphan and
  retry-canonicality cases.
- Unit test for aborted+willRetry tagging as recoverable.
- Live check with deterministic failure injection (see §7).

## 5. Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Event payload drift vs. types.d.ts (verified today) | Low | Pin assertions to the exact shape in §1.3; types test in P0-A |
| Double-counting failures (internal + host telemetry) | Medium | Single source of truth rule: host event owns cause; internal stage telemetry owns location; joined via synthesized `compactionSeq` (P0-A) |
| Retry storms inflating failure counts | Low | Canonicality rule: one terminal outcome per seq; retries counted once, failures kept as history |
| Stale docs contradicting runtime (maintenance notes, tracker) | Certain today | P0-B is a prerequisite merge; tracker updated via `ak issue`, DB-wins convention respected |
| ASC semantics change from terminate adoption | Eliminated in scope | Deferred out of this RFC entirely (P1-B decision, §8 non-goal) |

| Need to roll back the collector change | Low | Rollback safety derives from additive-only record emission: new records are appended alongside existing kinds, so reverting the collector branch restores pre-change semantics exactly; version-0 consumers ignore unknown record kinds |

## Appendix B — Review round 2: reviewer questions answered

**Q1: Does `compactionSeq` survive session fork/resume, or is it file-scoped — and
do dashboards need session-file grouping?**

Answered by decision in P0-A. The seq is scoped to the active collector session
context and deliberately does NOT attempt to survive replacement. Mechanics: each
record already carries the dynamically-resolved `sessionId`; the new design makes
the correlation key the composite `(sessionId, compactionSeq)`. Whenever pi swaps
the session file — fork, `new`, or a resume that materializes a fresh file — the
next `compaction_begin` simply starts a new counter under the new sessionId, so
uniqueness holds without any lineage tracking. Consequences: (a) dashboards must
group by `sessionId` before aggregating by seq — this requirement is stated as a
MUST in P0-A so consumer tooling encodes it; (b) retry sequences that span a session
replacement cannot be correlated across the boundary and will surface as an orphan-
terminal on the new side plus an unresolved begin on the old side; we accept this
rare residual rather than adding fragile lineage plumbing — it lands in
stalled-unknown/orphan buckets, which remain honest labels for genuinely severed
correlation. If post-upgrade data shows this residual is material, a follow-up can
add an explicit lineage id; not worth the complexity now.

**Q2: Who authors the AK issues for P0-B's two repos, and is the tracker-side issue
created before or after the docs edit lands?**

Answered by decision in P0-B. The same implementer authors both, but sequencing is
fixed: (1) tracker-side AK issue first, created in `softwareco/infra/issue-tracker`
(AK-backed repo), carrying the DB update — feature landed in 0.84.3 — plus the
review-ready classification for the Appendix A comment; (2) the monorepo docs edit
(standing-maintenance-notes.md §2) is authored second under the RFC's own monorepo
AK task and must reference the tracker issue id, so the note resolution points at
authoritative state instead of duplicating it. Rationale for tracker-first: the DB
is canonical and gates what the docs may truthfully claim; landing the docs edit
first risks recording a resolution whose authoritative record doesn't exist yet,
which is exactly the stale-doc class of problem this RFC exists to close. Both
issues are created before any edit lands; neither blocks on the other's completion,
only on its existence.

**Q3: What is the alerting story if orphan-failed (`orphan: true`) volume spikes —
silent tag or dashboard panel?**

Answered by decision: dashboard panel first, threshold alert after a baseline
quarter. Orphan-failures mean a terminal failure event arrived with no matching
begin — i.e., the collector missed the start (extension loaded mid-compaction,
collector restart, or host-side event loss). Volume expectations: near-zero in
steady state, so even modest spikes are signal. Concretely: (a) P0-A adds an
orphan-rate panel (orphans ÷ total failures, 24h rolling); (b) for the first
quarter it is panel-only — no paging — because the normal baseline is unmeasured
and early alerts would be noise; (c) after one quarter, promote to a soft alert at
the observed baseline + headroom (proposal: >5% orphan rate sustained over 24h),
owned by pi-telemetry's dashboard config; (d) a spike concurrent with a pi upgrade
is interpreted as an event-contract drift signal (check types.d.ts pin test first),
since payload/rename drift is the most likely cause of sudden begin-loss. This is
recorded as part of P0-A acceptance: the panel ships with the collector change,
not deferred.
