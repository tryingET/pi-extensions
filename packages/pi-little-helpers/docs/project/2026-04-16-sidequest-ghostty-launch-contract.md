# Sidequest Ghostty launch contract

## Operator truth

`/sidequest`, `/fresh-handoff`, `fresh_handoff_spawn`, and the other package-owned visible-session launchers should only claim **same-window tab attach** when the current session can actually do it.

If the active Ghostty session cannot prove that, an operator-requested visible-session launcher must open a **new Ghostty window** and say why. `/fresh-handoff` and `fresh_handoff_spawn` additionally launch a clean Pi session: it never passes `--fork`, and it auto-submits exactly one prompt generated by the `pi-session-compaction` owner surface. The automatic ASC observer is the deliberate exception: because it is optional diagnostic UI, it must remain headless rather than opening an untargeted tab or another window.

## Launch rules

1. Prefer the **current Ghostty session binary** when the current Pi session is already running inside Ghostty and the ancestor Ghostty process can be resolved.
2. When the current Pi session exposes `GHOSTTY_SURFACE_ID`, select the D-Bus endpoint from the actual controller Ghostty ancestor executable family before inspecting the bus: the normal origin/main family maps to `com.mitchellh.ghostty` at `/com/mitchellh/ghostty`; the transitional legacy `ghostty-sidequest*` family maps to `com.tryinget.ghosttysidequest` at `/com/tryinget/ghosttysidequest`. Resolve that well-known name's owner and its single unique user-D-Bus peer, then activate `org.gtk.Actions new-tab`. Never cross-fall back between executable families: with both brokers alive, a surface ID belongs only to its controller family. Send activation with `busctl --expect-reply=no`, terminate option parsing before embedded Ghostty argv, and let the controller surface ID select the exact window. Per-session launcher processes can expose stubs, so the nearest ancestor PID is not itself the action target.
3. During coexistence only, if the current session binary does not advertise `+new-tab` but the legacy sidequest wrapper does, operator-requested visible launchers may use that wrapper before falling back to a new window. The normal origin/main path is the primary contract and must not require the wrapper; remove this compatibility rule after the legacy surface population reaches zero.
4. Only fall back to the Ghostty sidequest wrapper by default when no current-session Ghostty ancestor can be resolved.
5. Only attempt same-window tab attach when all of the following are true:
   - platform is Linux
   - Pi is running inside Ghostty (`TERM_PROGRAM=ghostty`)
   - the chosen Ghostty command advertises `+new-tab`
6. `GHOSTTY_SURFACE_ID` is an optional targeting hint, not a hard prerequisite. Pass it only when present **and** the chosen Ghostty build supports the `+new-tab --surface-id` action flag (Ghostty 1.4+); do not force a window fallback solely because it is absent or unsupported.
7. Do **not** force Ghostty `--title=...` for sidequest launches, because Ghostty treats that as a fixed title and will ignore later dynamic title updates. Seed the desired base title through `PI_SESSION_PRESENCE_TITLE_BASE` instead so `session-presence` can append the live `· <full-32-hex-session-id-token>` suffix.
8. Do not trust Ghostty `+new-tab --working-directory=...` alone for peer cwd correctness; receiving tabs can inherit the current surface cwd. The launched shell command must explicitly `cd` into the requested cwd before starting Pi.
9. For **new window** launches, do **not** rely on `ghostty +new-window -e ...` to carry the command payload. Launch a fresh Ghostty window directly with `ghostty -e ...` (plus working-directory/config args) so Pi actually starts in that window. A direct Ghostty window may itself be the long-lived GUI process, especially when `gtk-single-instance=false`; therefore it must be detached from the controller command timeout.
10. A detached direct-window process is not successful merely because the OS accepted `spawn`. The new terminal shell must atomically rename an exact random-token file onto a private per-attempt handshake path immediately before invoking Pi. Only rejection before OS-level spawn confirms no peer-command effects. Once spawn succeeds, any nonzero exit, signal, timeout, or unconfirmed handoff remains effect-indeterminate because a descendant may already hold the attempt; removing an unconfirmed handshake directory makes a later atomic rename fail closed before Pi whenever cleanup wins the race.
11. If any hard prerequisite is missing, launch a new Ghostty window directly instead of attempting same-window tab attach.
12. Retry a failed same-window launch with a direct new window only when the first attempt proves `confirmed_no_effects`. A killed, timed-out, cancelled, or otherwise indeterminate attempt must never trigger an automatic fallback, because the first peer may already be starting and a retry could duplicate mutations, evidence, and model spend.
13. Report launch success only after its transport-specific acceptance proof: successful awaited activation for a targeted tab, or the private command-admission handshake for a detached direct window. This proves transport only, not Pi readiness, peer completion, or task effects. An executor result marked `killed` is effect-indeterminate even if its normalized exit code is zero.
14. After a successful tab launch request, perform a brief best-effort placement check through `session-presence`: match the launched Pi session by cwd/title, compare the controller and child Ghostty ancestor PIDs, and warn when the child landed under a different Ghostty window/process. This check corrects the operator-facing message; it does not turn terminal placement into task/evidence authority.
15. Controller D-Bus targeting must first prove a recognized executable-family endpoint, resolve that endpoint's well-known owner to exactly one unique bus name, and verify through `/proc/<owner>/exe` that the owner is the exact same Ghostty build as the controller. This rejects a stale packaged singleton and same-user bus-name claimants before sending embedded argv. Then encode the controller surface ID as a bounded unsigned 64-bit integer, pass launch arguments as argv elements, terminate `busctl` option parsing before embedded arguments, and avoid waiting for the action reply. The normal and transitional legacy mappings are disjoint. Unknown/custom executable families fail closed rather than guessing an application identity. If direct activation for an operator-requested visible session proves no effects, retain the honest new-window fallback; if it is killed or indeterminate, do not retry automatically.
16. The automatic ASC observer may reuse this exact targeting path with an explicit read-only Node renderer command instead of a Pi peer command, but it selects `controller-tab-only` placement. Capability probes must use the actual controller ancestor executable and ignore `PI_SIDEQUEST_GHOSTTY_BIN`; it requires the exact-build single-instance server D-Bus target and the controller's surface id, and it must not substitute an untargeted wrapper tab or use the ordinary new-window retry. Missing or failed exact targeting records one observer failure and leaves ASC execution headless. This does not make the renderer a child-session owner: launch success is observer placement only, renderer exit never cancels ASC execution, and no-UI callers remain headless.
17. `/fresh-handoff` and `fresh_handoff_spawn` must capture bounded read-only Git HEAD/status and AK claimed/ready-task readbacks through the same implementation, then generate before launch through `@tryinget/pi-session-compaction/handoff-generation`, preserve the controller model and thinking level, omit `--fork`, and pass the generated handoff once as Pi's initial prompt. Unavailable readbacks must stay explicit and non-authorizing; the fresh session must verify owner state again before mutation. A generation failure launches nothing. Terminal launch success proves transport only, not generated-content correctness or task completion.

## Non-goals

- `/sidequest` does **not** talk to Niri directly.
- `/sidequest` does **not** invent or recover a missing `GHOSTTY_SURFACE_ID`; it only forwards one when the environment already provides it and the active Ghostty build supports that action flag.
- `/sidequest` does **not** claim tab success unless the chosen Ghostty command returns success for the `+new-tab` launch. If the sidequest wrapper is available and tab-capable, it may be the chosen command even when the ancestor Ghostty binary is older/stock.
- The automatic ASC observer does **not** inherit wrapper/new-window latitude. Without an exact executable-family endpoint, unique single-instance peer, and controller surface ID, it stays headless and warns once.
- Transitional recognition of `com.tryinget.ghosttysidequest` does not make it an end-state dependency. After the last legacy controller is gone, remove its endpoint, wrapper fallback, tests, and documentation in the retirement slice.
- The post-launch placement check is best-effort and local-only. If no matching `session-presence` sidecar appears before the short timeout, `/sidequest` leaves the original launch result intact instead of blocking the child session.

## Verification expectations

Minimum verification for changes that touch this path:

```bash
cd packages/pi-little-helpers
node --test tests/asc-execution-observer-launch.test.mjs tests/sidequest.test.mjs
npm run check
npm run release:check:quick
# Reality-anchored: verify targeting against the live Ghostty single-instance desktop (skips with a reason when absent).
npm run reality:check
```

For full installed-artifact validation, `npm run release:check` should also execute the package `scripts/release-smoke.sh` path and confirm the published extension still registers `/sidequest`, `/fresh-handoff`, and `fresh_handoff_spawn` from the installed package surface.
